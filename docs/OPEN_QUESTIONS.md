## 1. Repo / tooling (from Step D, §7)

### Q-D1 — Package manager
**[Q]** pnpm (recommended) vs npm vs yarn workspaces?
**Recommendation:** **pnpm.** Fast, disk-cheap, trivial `@df/*` linking. npm
works as fallback; the lockfile is the only commitment. → **DECIDE before M0.**

**Recommendation:** **Node + Vite for v1.** Keeps the build simple and the
provider boundary clean; `apps/studio/main/` is structured so Electron is a
later packaging option, not a rewrite (REPO_LAYOUT §2). → **DECIDE before M0.**

`docs/` now?
**Recommendation:** **Root through Phase 0, move to `docs/` at M0.** Currently
at root for visibility; REPO_LAYOUT §6 already specifies the move. Trivial.
→ **DECIDE at M0 start.**

### Q-D4 — Stable-ID prefix scheme *(already resolved in Step E)*
**[S]** Confirm the `kind_...` convention (`char_`, `fac_`, `quest_`, `scene_`,
`canon_`→`fact_`, `state_`, `rel_`, `beat_`, `dlg_`, `review_`, `prop_`,
`ctx_`, `project_`) plus the single `__` sub-segment rule.
**Status:** **IMPLEMENTED & TESTED** in `@df/schemas` (Step E, 13 tests green;

you're happy with the sample IDs.**

### Q-D5 — Sample project: committed vs seeded

**Recommendation:** **Committed.** It's the regression fixture for the entire

for no gain in v1. → **DECIDE before M0.**

## 2. Schema decisions (from Step E)

### Q-E1 — Opinion/quest conditions as free text
**[S]** `Opinion.canChangeCondition`, `QuestStage.entryCondition`,
`completionCondition`, `failureCondition` are natural-language strings in v1.
The Context Compiler *surfaces* them; it does not *evaluate* them.
**Recommendation:** **Keep NL in v1.** A formal state-machine DSL is a large
undertaking explicitly out of scope (NON_GOALS §3.5). Flag for post-MVP. →
**DEFERRED to post-MVP; default NL.**

### Q-E2 — Relationship dimension scale
**[S]** `RelationshipDimension` is `-100..100` integers. No threshold model is
prescribed in the schema; named states are authored separately and the compiler
matches them.
**Recommendation:** **Keep -100..100, keep numbers out of dialogue.** The scale
is arbitrary but stable; the *named state* (`hostile-but-grudging-respect`) is
what surfaces in prompts, not raw numbers (per contract §3.5). → **DECIDE
before M5** (when mutations land); interim default OK.

### Q-E3 — Quest choice `variablesChanged` shape
**[S]** Currently `{key, from?, to?}` with `from`/`to` as strings — a
typed-but-loose key/value-ish note. Not a real variable engine.
**Recommendation:** **Keep loose in v1.** Real quest variables need the
state-machine work deferred in Q-E1. The strings are descriptive enough for the
reviewer to check "did the choice do what it claimed." → **DEFERRED to M5/post-
MVP; default loose.**

### Q-E4 — ESM `.js` import specifiers in `.ts` sources
**[S]** Sources use `.js` specifiers (e.g. `import ... from "./common.js"`)
compiled via `tsc` + `moduleResolution: Bundler`. Works under tsc, vitest, and
the emit script uniformly.
**Risk:** Contributors can't run `.ts` files directly with
`node --strip-types` without a specifier rewriter.
**Recommendation:** **Keep.** Every execution path goes through `tsc` or
`vitest` in v1; the uniformity is worth more than direct-node-run convenience.
Document in `README.md` at M0. → **DECIDE before M0** (documentation task).

### Q-E5 — `z.record()` key validation
**[S]** `Project.templateDefaults`, `Project.locks.characterProfileFields`,
and `Quest.variablesChanged` use `z.record(z.string(), z.unknown())` or nested
records — keys are unvalidated.
**Recommendation:** **Acceptable for v1** for template defaults and lock
registries (free-form UI state), but the `stable-id`-keyed records should be
validated at the *storage* layer in M1, not the schema layer (the schema can't
know which ids exist). → **DEFERRED to M1** (`@df/storage` referential-
integrity check).

## 3. Schema gaps surfaced in Step F (must close in M1)

### Q-F1 — No `ContextPackage` schema *(blocking)*
**[S]** `context/*.ctx.json` (Stage 1 output) has **no contract schema**. The
sample ships one as illustrative data; it is currently skipped by the validator.
**Recommendation:** **Add `ContextPackage` as the first M1 deliverable.** It's
the single most-inspected artifact when a generation goes wrong (ARCHITECTURE
§5) — leaving it unvalidated contradicts constraint #12. The Step F sample
gives the shape to derive it from. → **M1, blocking.**

### Q-F2 — `terminology.json` / `timeline.json` not contract-validated
**[S]** These are loose helper arrays in the sample; only `world-facts.json`
(CanonFact[]) is validated.
**Recommendation:** **Add `Terminology` and `TimelineEvent` schemas in M1** if
they're going to be first-class Context Compiler inputs (the faction schema
already embeds terminology; timeline drives ordering). Low cost, high
consistency. → **M1.**

### Q-F3 — `contentHash` is a placeholder
**[S]** Every artifact ships `contentHash: "sha256:<slug>"` — not a real hash.
**Recommendation:** **Real hashing is an M0 deliverable** in `@df/core` (the
`Versioned` schema constrains the *shape* `min(8).max(128)`; the *algorithm* is
core's job). Hash must be over the meaningful content *excluding* `version` and
timestamps, per ARCHITECTURE §7. → **M0.**

## 4. Risks (cross-cutting)

### R-1 — Provider output unreliability *(top risk)*
**[R]** GLM (any model) will sometimes return malformed JSON, drift voice, or
invent facts. This is the core technical risk.
**Mitigations already in the contract:** validate-before-store (constraint
#12), beat-plan-then-draft (two calls), knowledge-leak detection, canon-
proposal inbox, anti-sample lines, report-don't-rewrite.
**Residual:** retries/partial-repair need careful design so a bad line doesn't
force a full-scene regen. **Owner: M3/M4/M6.**

### R-2 — Long-context-as-memory temptation
**[R]** GLM-5.2's 1M-token window invites dumping the whole project into one
prompt, eroding the Context Compiler's "small precise package" discipline.
**Mitigation:** ARCHITECTURE §5 makes the `ContextPackage` an inspectable,
bounded artifact; ACCEPTANCE M4 tests assert it excludes forbidden facts and
selects only permitted ones. **Owner: M4.**

### R-3 — Scope creep via "consistency"
**[R]** The consistency engine could grow without bound (sentiment, profanity,
style scorers…). Each new checker is a maintenance + false-positive cost.
**Mitigation:** NON_GOALS §3.4 explicitly excludes dedicated scorers; every new
checker must pass the "planted contradiction" human gate (M6) before adoption.
**Owner: M6+.**

### R-4 — Goldens becoming a bottleneck
**[R]** Golden-output tests can make CI flaky if they pin model-dependent prose.
**Mitigation:** ACCEPTANCE §7 — goldens guard against *drift*, never against
*quality*; quality is a human gate. Goldens are versioned with the prompt
template. **Owner: M3/M4.**

### R-5 — Premature schema lock-in
**[R]** 13 schemas authored before any UI or pipeline exists; some field
choices may prove awkward under real editing.
**Mitigation:** `version` on every artifact + the M1 adversarial-authoring
human gate ("express one new character of each type; find no missing/forced
field"). Schemas are versioned, not immutable. **Owner: M1.**

### R-6 — Windows-path fragility
**[R]** Development is on Windows (`win32`, Git Bash). The validator script
uses forward-slash paths and `node:fs`; the `__` ID rule and filename-derived
IDs must stay case-insensitively safe.
**Mitigation:** IDs are lowercase snake_case (no collision risk); scripts use
`node:path`. Flag for the M0 CI matrix (run tests on Windows + Linux).
**Owner: M0.**

## 5. Decisions I made unilaterally (call out anything you'd reverse)

These were judgement calls made during Steps A–G to keep moving. Each is
reversible; none contradict the design doc.

1. **Two I/O packages** (`storage` + `providers`) instead of one "infra" package
   — keeps fs and network isolated and individually swappable (REPO_LAYOUT §3).
2. **Git as the merge/history tool**, no in-app undo engine or concurrent-edit
   merge (NON_GOALS §3.1–3.2) — matches the "human-readable version-controlled
   JSON" contract.
3. **Stage artifacts persist to disk**, not just in-memory — makes any stage
   independently re-runnable and inspectable (ARCHITECTURE §2).
4. **Pure/I-O split mandated** in the pipeline so the whole thing is unit-
   testable with fixtures, no network (ARCHITECTURE §9).
5. **`.js` import specifiers in `.ts`** under `moduleResolution: Bundler`
   (Q-E4 above).
6. **Model output quality is never a CI gate** (ACCEPTANCE §7).
7. **Relationship numbers stay out of dialogue**; only the named state surfaces
   (Q-E2, contract §3.5).
8. **Treated the existing `PLAN.md`** (the simpler Python single-file tool) as
   superseded by the Dialogue Foundry doc, left it untouched on disk.

## 8. Post-Phase-0 decisions

### Q-A1 — No API keys / no paid model calls (decided 2026-08-05)

**Decision:** The application **never** makes a real LLM call. No `GLM_API_KEY`
is read, no network egress to a model provider, ever. Every code path —
including the UI's Generate button — uses a **mock provider** that returns
canned, deterministic, schema-valid output.

**Scope impact:**
- **M3 (profile generation), M4 (dialogue generation), M6 (consistency engine):**
  built and fully tested with the mock provider. The pipelines, schemas,
  validation, locking, and approval flow all work for real; only the *source*
  of the generated text is mocked rather than a live model.
- **Human gates** for M3/M4/M6 ("three distinct generated characters", "voice
  holds across states", "checker catches planted contradictions") are met by
  inspecting the mock's output and the planted-contradiction tests — not by
  judging live model quality. This is an explicit, accepted limitation.
- **The `DialogueAIProvider` interface is unchanged** (constraint #9). A real
  GLM/Claude/local implementation can be added later by anyone who opts in;
  the default build ships mock-only.

**Why this is safe:** the contract's hardest guarantees (validate-before-store,
propose-not-impose, no silent canon edits, locking) are all exercised
identically against mock output — the mock is just another untrusted provider.
The architecture's value is the *pipeline*, not the model behind it.

**Supersedes** any implication in earlier docs that GLM-5.2 is wired by default.
`providers/` ships the interface + the mock; no GLM client code is written.
